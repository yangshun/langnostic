Langnostic translates localization files and Markdown documents through format
plugins. The CLI manages discovery, batching, AI requests, and progress reporting.
Plugins decide what needs translation and how to update files.

## AI providers

Langnostic uses the [AI SDK](https://ai-sdk.dev/) to access compatible language
models. You supply the provider package, credentials, and model through
`ai.model`. Examples in these docs use `openai('gpt-6.1-sol')`.

Provider catalogs change independently of Langnostic. Check availability and
structured-output support before selecting a model:

- [OpenAI models](https://developers.openai.com/api/docs/models) and the
  [AI SDK OpenAI provider](https://ai-sdk.dev/providers/ai-sdk-providers/openai).
- [Google models](https://ai.google.dev/gemini-api/docs/models) and the
  [AI SDK Google provider](https://ai-sdk.dev/providers/ai-sdk-providers/google).
  A current example is `google('gemini-3.8-flash')`.
- [Claude models](https://platform.claude.com/docs/en/models/overview) and the
  [AI SDK Anthropic provider](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic).
  A current example is `anthropic('claude-sonnet-5-5')`.

Changing the configured model does not itself invalidate existing translations.
Provider usage is billed under your provider's terms.

## Supported formats

Official plugins are installed separately from the CLI:

| Plugin                        | Source content                                    | Default strings per request |
| ----------------------------- | ------------------------------------------------- | --------------------------- |
| `@langnostic/plugin-formatjs` | Flat string maps and FormatJS message descriptors | 50                          |
| `@langnostic/plugin-mdx`      | Markdown/MDX blocks and frontmatter fields        | 20                          |

FormatJS catalogs can contain ICU messages, tags, and placeholders:

```json
{
  "welcome": {
    "defaultMessage": "Welcome, {username}!",
    "description": "Greeting for a signed-in user"
  },
  "itemCount": {
    "defaultMessage": "{count, plural, =0 {no items} one {# item} other {# items}}",
    "description": "Number of items in the cart"
  }
}
```

Nested JSON, XML, YAML, TOML, and other localization schemas require a compatible
custom plugin. See [Using plugins](/docs/plugins) for setup and authoring.

## Change detection

### FormatJS catalogs

The plugin compares message IDs between source and target files. Missing IDs
need translation; IDs removed from the source are removed from target files on
a real run. Existing target values are kept.

Edits to source text or descriptions under an existing ID do not trigger
retranslation. Remove that ID from the relevant target catalog to request a new
translation, or update it manually.

### Markdown/MDX

The plugin hashes source blocks and frontmatter fields, storing progress in a
`*.langnostic.json` registry beside each source document. It can reuse
translations for tracked blocks and translate new or modified source content.
Removal-only and reordering-only changes can update files without AI calls.

Keep registries in version control. Missing registries or a target block count
that differs from the registry can trigger full content retranslation. Manual
edits that change block structure can break the association between source and
target blocks. Read [MDX change detection](/docs/plugins#mdx-change-detection)
before editing target structure.

## Format-aware translation

Plugins provide instructions for their content. The FormatJS plugin asks the model
to retain ICU placeholders and tags; the MDX plugin provides Markdown/JSX guidance
and asks it to preserve inline code.

These are model instructions, not a syntax-preservation guarantee. MDX code
blocks and JSX blocks are also sent to the model. The runner validates the shape
and completeness of translation results, but does not validate ICU syntax,
placeholder equivalence, JSX, or unchanged code examples.

Review and validate generated content before using it. Markdown and frontmatter
are reserialized, so original whitespace and formatting are not retained exactly.

## Batching and concurrency

Strings from a source file share a batch ID. The runner divides each batch into
requests according to `stringsPerRequest`, keeping related strings together.
Each source string can request translations for multiple locales.

Set a group's `stringsPerRequest` to override its plugin's default. The global
`concurrencyLimit` controls concurrent requests and defaults to **5**. Both
settings must be positive integers.

Results are passed to the plugin after all requests for a batch succeed. The
official plugins use atomic writes for individual files; a run is not one
transaction across all files or locales.

## Preview and debug output

`--dry-run` shows pending file batches and string counts without AI requests or
file changes. `--debug` runs translations and saves prompts, responses, and
errors in `.langnostic/runs/`.

See [CLI](/docs/cli) for the exact output and
[Configuration](/docs/configuration) for available options.
